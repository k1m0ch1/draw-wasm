Platform Architecture · Executive Brief

draw-wasm

A local-first collaborative whiteboard in the spirit of Whimsical: a Rust engine compiled to WebAssembly does all the drawing in the browser, one small Rust server does all the coordination, and a single SQLite file is the entire database. Drawings are private by default — nothing leaves the device until the user chooses to share them.

01

The system at a glance

Three tiers. The browser carries the entire drawing engine, so the server stays tiny and the canvas never waits on the network.

Data path. Offline / private documents are written entirely in the browser (IndexedDB, no server involved). Online / cloud documents use the server: SQLite for storage and a WebSocket for live collaboration. The live instance is https://coret.app.

One Rust process is the whole backend: it serves the app, guards every write, keeps live rooms running, and stores everything in a single database file.

Persistence without a DBA

Live rooms sit in memory and flush to SQLite within seconds of going quiet — a restart can lose seconds, never a drawing.

Store-once images

Every image is addressed by its SHA-256 hash: ten pastes of the same screenshot are stored once, served forever immutable.

Nothing admin on the network

Maintenance (purge test data, stats) runs as a CLI inside the container only — there is no admin route to attack.

How a drawing travels between people

The server is the single orderer: every change gets a sequence number, everyone sees the same order, and nobody's edit is silently dropped.

05

Private by default, public by choice

There is no halfway state: a drawing is either in one browser, or it is a public room with a shareable link and explicit access control.

Private · default

Lives in the browser

Every drawing starts in IndexedDB on the user's device. No account, no upload, no telemetry — the server never sees it. Local drawings have no share link at all.

“Store on cloud”one deliberate click
user is told it becomes public
Public · opt-in

Shared room with a link

Anyone with the link can view. Editing is open by default; the room owner can set an edit password, which makes everyone else read-only until they enter it. Only the owner can delete the room and its documents.

Identity without accounts

A random token per browser; the server stores only its cryptographic hash. Display names are optional — leave it blank and you join as a random smiley.

Ownership, not logins

The room claimer's browser holds the owner token. There is no password database to breach and no profile data to leak.

Editable GIFs & images

Pasted images are shrunk client-side and de-duplicated by content hash; GIFs keep their original bytes so they stay animated.

06

Security posture

Every rule below is enforced by the server — never by hiding buttons in the interface. Each has an automated test that fails if the rule breaks.

Server-side enforcement

Every write — WebSocket op, upload, delete — is authorised at the server. A modified client gains nothing.

Room isolation (IDOR-tested)

Documents cannot be reached through another room's path; owner tokens from room A grant nothing in room B. Verified by attack tests.

Password-protected editing

Optional room password, stored as an argon2id hash, compared in constant time, rate-limited. Wrong password: read-only.

Abuse limits

Per-IP rate limits that can't be dodged with forged headers, request-size caps, magic-byte image checks, no SVG uploads.

Hardened runtime

Non-root container, read-only filesystem, all capabilities dropped, memory/CPU/process caps, strict CSP, no admin endpoint on the network.

Deploy safety

Version handshake: after an update, old tabs are told to reload instead of silently failing; reconnects back off and lose no edits.

07

Capacity & scale — what could hurt us

Two things grow non-linearly: broadcast fan-out in a crowded room (every edit reaches every person — N editors means N×N messages) and decoded image memory on the client. These guardrails cap both, by design.

GuardrailLimitWhat happens at the edge
Editors per document20 concurrent (+ the owner)everyone else joins as a live viewer in a FIFO queue — auto-promoted the moment a slot frees
Images≤ 2,000 px edge · 2 MB maxshrunk in the browser before upload; the server refuses anything larger
Animated GIFs≤ 3 MB, original byteskept byte-identical so they stay animated; larger is refused with a clear message
Client memory budget< 100 MB typicaldecoded images live in an LRU cache with a pixel budget; GIF frames capped
Elements / document5,000further edits are refused — the doc stays responsive
Document size4 MB serializedbounds snapshots and reload cost
Connections30 per IPblunt but effective against one-machine floods

The 20-editor room

A room can hold many viewers, but only 20 editors at once — so the expensive N×N path stays bounded. Viewers still see every stroke live; the queue promotes in join order, no refresh needed.

The memory diet

Decoded bitmaps sit in an LRU cache under a pixel budget (re-decoded on demand from local storage), GIF frame caches are capped, and the WASM engine trims its allocations — targeting under 100 MB typical.

Residual risks we watch

Image hot-linking (cache at the CDN solves it), cursor fan-out to very many viewers, and the reload wave right after a deploy (already jittered). None are unbounded today.

08

Deployment & operations

One box, one container, one database file. Small enough to reason about, cheap enough to forget.

Footprint

A single Docker container (512 MB RAM, 1 CPU cap) behind nginx with Let's Encrypt TLS, fronted by Cloudflare. Binds to localhost only.

Data durability

SQLite on a named volume — documents, images and history survive redeploys and restarts. Live edits flush within seconds.

Deploys

Manual, one command, from a clean build. Health-checked, with automatic rollback of a bad nginx config and a no-side-effects baseline check of the host.
